# ShellRS user manual

[Back to README](../README.md) · [简体中文](manual.zh.md)

An SSH host manager built on GPUI Kit, with saved hosts and groups, login credentials that several hosts can share, local terminals, multiple SSH terminals, file uploads and downloads over a terminal’s connection, and SSH port forwarding.

The three icons after “ShellRS” in the title bar switch what the left sidebar shows: the host list, the port forwarding list or the credential list. When the sidebar is hidden, clicking one of them shows it again. The left sidebar's visibility is saved automatically and restored on the next launch; it is shown on the first launch. The sidebar toggle sits just past the host panel’s right edge, with its icon and its tooltip (“Hide sidebar” or “Show sidebar”) following the sidebar’s state. Drag the host panel’s right edge to resize it: it’s 280 pixels wide by default and can go down to 180, and the next launch keeps the width (see General → Window). The toggle moves with the edge as you drag, stays to the right of the three icons when the panel is narrower than they are, and stays put when the sidebar is hidden.

Only one ShellRS runs at a time: opening it again while it’s running brings the existing window to the front, and the newly launched copy quits. Two copies would each load the hosts into memory and write them back to the same database, overwriting each other’s changes. (Copies pointed at different data folders with `SHELLRS_DATA_DIR` count as different and can run side by side; so do the installed and portable copies on Windows.) To see two terminals side by side, drag a tab into a split.

On macOS, the close button at the top left of the window only hides ShellRS: open connections, file transfers and port forwards keep running. Click the Dock icon to bring the window back with all its tabs. To actually quit, press ⌘Q or right-click the Dock icon and choose Quit. The menu bar is the same as in other Mac apps: the ShellRS menu has About, Settings, Hide ShellRS (⌘H), Hide Others (⌥⌘H), Show All and Quit, and the Window menu has Minimize (⌘M) and Zoom. On Linux, closing the window quits.

Windows quits when the window is closed by default. Turn on “Minimize to tray on close” under “Settings → General → Window” to hide the window instead, keeping connections, transfers and port forwards running. Click the tray icon or choose “Show window” from its context menu to restore the window. Choose “Quit” to exit. Starting ShellRS again or using the system-wide show shortcut also restores the window. This option is off by default and appears only on Windows. If the tray icon cannot be created, ShellRS reports the error and keeps the window open.

## Hosts

Each item saved in the left sidebar is a host: an address, a port and a way to authenticate. To log in to the same machine as different users, save it as two hosts.

“Protocol”, below the name, is SSH, Telnet or Serial. You can change it when editing a host: what the protocols’ forms share (the name, address, group, connection, notes and so on) carries over, and the rest takes the new protocol’s defaults. An SSH host that other hosts use as a jump host, or that port forwards go via, stays SSH. SSH hosts come first below; Telnet and serial hosts are at the end of this section.

The host dialog’s “Authentication” has three options:

- **Password**: enter a username and password; the password is kept in the system keychain. Leave the password empty to be asked at each connection. Only the password is used: the SSH agent and private keys aren’t tried first. When the server takes passwords only through keyboard-interactive authentication (ESXi, for one), the saved password answers its single hidden question; other questions, such as a verification code, are still asked.
- **Credential**: choose a saved credential. The username and the way to log in both come from the credential (see “Credentials” below), so the dialog no longer asks for a username or password. “Test connection” also uses the password saved in the credential. To log in with a private key, create a key credential.
- **No password**: enter only the username. ShellRS tries logging in without authentication, then the SSH agent, then the default private keys in `~/.ssh` (`id_ed25519`, `id_ecdsa`, `id_rsa`), the same as the `ssh` command does by default. If the server asks for a password, the connection fails with the reason instead of asking; if the server asks for a verification code after the key, you’re still asked for it.

Whichever you choose, ShellRS first asks the server whether it allows logging in without authentication, and logs straight in if it does. If “Test connection” runs with “Password” chosen but no password entered, it tries what “No password” would (no authentication, the SSH agent, the default private keys) and explains why if it can’t connect.

“Connection”, below “Group” in the host dialog, decides how to reach the host. Terminals, file transfers, port forwarding and “Test connection” all follow it:

- **Direct**: the default. This computer connects straight to the host’s address and port.
- **Jump hosts**: connects through other saved hosts, with as many hops as needed. A row of labels in the box shows the whole route (“This computer → aliyun-99 → zentao → This host”), and below it each jump host has a row: “×” removes it, and “Add jump host” searches by name or address. To change the order, remove jump hosts and add them again. ShellRS logs in to the first jump host, which connects to the second, and so on, until the last one connects to the host. Each jump host uses its own address, port, authentication (password, credential or no password) and known hosts entries; on the first connection you’re asked about each one’s host key, and the prompt says which jump host it is. A jump host’s own “Connection” has no effect here: for several hops, list them all here in order. Enter the host’s address as the jump hosts’ network sees it, such as an internal address.
- **Proxy**: connects through an HTTP proxy (`CONNECT`) or a SOCKS5 proxy, chosen in the drop-down. Enter the proxy’s address and port (such as `127.0.0.1:7890` on this computer); if the proxy needs authentication, also enter a username and password. The password is kept in the system keychain and shared by hosts that go through the same proxy with the same username. The proxy resolves the host’s address. If the proxy requires authentication but has no password, or rejects the username and password, the connection fails with the reason instead of asking.

Each open tab keeps the host as it was when the tab opened: editing the host (its name, address, protocol and so on) leaves it alone, and its title, icon, status bar and reconnecting all go by what it opened with; open a new tab for the new settings. Deleting a host doesn’t close its tabs either; their menus just lose “Edit host…” and the other items that need the host itself. When you delete a host that other hosts use as a jump host, the confirmation says how many hosts use it. Afterwards their jump host lists keep a “Deleted host” row, and connecting fails right away instead of quietly connecting directly or skipping a hop; edit those hosts to remove it or choose another. Open connections aren’t affected.

**Not implemented yet: combining jump hosts with a proxy, reordering jump hosts by dragging, HTTPS proxies, and showing the connection type in the host list.**

The last field in the dialog is “Notes”, which can span several lines (Enter starts a new line): what the machine is for, who looks after it, when it expires and so on. Notes are kept only in the local database and don’t affect connecting.

The icon before a host is the badge of the system found when connecting, or the first letter of its name until one is found. An icon without a brand color (the letter, and the macOS and AlmaLinux badges) gets a color from the address, or a serial host’s port; the same address always gets the same color. Telnet and serial hosts have no system to find, so their icon is always the first letter of the name.

Hover over a host and `user@address:port` appears at the right of its row, with its notes below if it has any (only the first 6 lines of long ones). A host’s context menu has “Connect”, “Edit host…”, “Duplicate”, “Copy IP” (“Copy hostname” when the address is a domain name), “Copy ID” and “Delete”. “Copy ID” copies the host’s 16-character random identifier (like `Jwg5rHvXCxw89paM`), which other tools use to identify the host: it’s generated when the host is created and stays the same when you rename the host or change its address; a duplicated host gets a new ID, and deleted IDs are never handed out again. When no tabs are open, the center area shows the “Recent” list; double-click a host or press Enter to connect. Right-clicking a host there opens the same menu and selects the host.

“Find a host”, to the left of “New host…” above that list, opens a search box listing every saved host: recently connected ones first, the rest by name, each row showing its group and `user@address:port`. Type part of a name, address, username, notes or group to filter; with several words separated by spaces, all of them must match. Nothing is highlighted when it opens; once you type, the first match is highlighted and Enter connects to it. You can also move with ↑↓, or click a host to connect to it.

The search box above the host list (⌘K, or Ctrl+K on Windows and Linux) filters hosts by name, address and username, and finds groups by name: when a group’s name matches, the group is listed with all its subgroups and hosts. Results are expanded, and matching hosts appear together with every level of group above them. Enter connects to the first matching host (in list order; hosts listed only because their group matched don’t count). Esc clears the search.

Drag a group or host above or below another item of the same kind to reorder items at the same level; drag a host onto a group to move it into the group, and drag a group onto the middle of another group to make it a subgroup. Drag to an empty part of the list to move an item back to the top level. Groups always come before hosts at the same level, and the order and which groups are expanded are saved in the local database. Reordering by dragging is paused while you search.

**Importing hosts**: “Import from ~/.ssh/config…” and “Import from ~/.ssh/known_hosts…” in the host list title bar’s “…” menu, and in the context menu of the list’s empty space, add the hosts OpenSSH already knows about in one go. The dialog lists the hosts in the file first; select and adjust them, then click “Import N hosts”. Hosts with the username `git` and code hosting addresses such as GitHub, GitLab, Bitbucket and Gitee are for pushing and pulling code, not logging in, so they aren’t listed:

- **~/.ssh/config**: every name on a `Host` line is a host (patterns with `*` or `?`, and names starting with `!`, aren’t), named after it. Settings are taken the way `ssh -G` takes them: every block that applies (wildcard ones such as `Host *` included) is read in file order, and the first value of each setting wins. `HostName`, `Port`, `User` and the first `IdentityFile` are read; without a `User`, your username on this computer is used. `Include` is followed (relative paths are under `~/.ssh`, wildcards work). `Match` blocks are skipped (except `Match all`); `ProxyJump` and `ProxyCommand` aren’t imported, so the hosts connect directly — set up jump hosts in the host dialog afterwards. Several names for the same address, port and username give one host.
- **~/.ssh/known_hosts**: lists the hosts you’ve connected to, one per host whatever its keys, with the port read from `[address]:port`. The file has no usernames, so each is set to `root`. Hashed entries (starting with `|1|`, the default on Ubuntu and Debian) can’t be read back; the dialog says how many there are. Host keys aren’t copied into ShellRS’s own known hosts file, so the first connection still asks whether to trust the key.
- **Each row**: the name, group and username can be changed. A group is a path such as `Production/East`, created if it doesn’t exist, and one new path makes one group; leave it empty for no group. “Status” says “New”, or “Saved” when a host with the same address and port is already saved; such a row can’t be selected, as an import never changes the hosts you have.
- **Authentication**: when `IdentityFile` names a private key on this computer that isn’t a default one (`~/.ssh/id_ed25519`, `id_ecdsa`, `id_rsa`), the row uses a key credential: a saved one for the same key and username if there is one, otherwise a new “Local file” credential made by the import (named after the key file; rows sharing a key and username share one), with a copy of the key in `keys/` in the data folder; importing the same key file again recognizes that copy and makes no second credential. Other rows log in with “No password” (which tries the SSH agent and the default keys). Each row’s “Authentication” menu can change this to “Password” or another credential; with a saved credential, the username comes from it.
- **Choose file…**: reads another file of the same kind; relative `Include` paths are still under `~/.ssh`. In the macOS file picker, press ⌘⇧. to show hidden folders such as `.ssh`.

**Telnet hosts** are reached over Telnet: switches and routers, console servers (one port for each device’s console), device consoles in GNS3 or EVE-NG, and embedded devices. Choose “Telnet” under “Protocol” in the host dialog:

- **Address and port**: as for an SSH host; the port is 23 by default (for a new host, the port follows the protocol between 22 and 23 until you change it). The name is the address if left empty.
- **Log in automatically**: off by default, so you type the username and password in the terminal once connected. Turn it on and choose under “Authentication”:
  - **Manual**: a username and a password, either of which may be left empty. The password is kept in the system keychain; without one, only the username is typed and you type the password once connected. For a device that asks only for a password (such as a Cisco device with just a `line vty` password), leave the username empty.
  - **Credential**: a password credential, which gives both the username and the password. Only password credentials are listed: keys and the SSH agent are no use to Telnet.
  - **Username prompt / Password prompt**: what the device shows when it asks for each. Left empty, the usual ones are recognized (`login:`, `Username:`, `User Name:` and `Password:`); filled in, only that text is. Matching ignores case and spaces at the end of the line, and looks only at the end of the line the cursor is on.
- **How it logs in**: at the username prompt it types the username, and at the password prompt the password, each once. A device that asks for the password first gets just the password. After a failed login, when the username prompt comes again, it leaves you to it; and if you press a key before it types, it doesn’t type at all.
- **Connection**: as for an SSH host: direct, through SSH jump hosts, or through a proxy. Through jump hosts, the last one connects to the Telnet host’s address and port, so enter the address as seen from there. A Telnet host can’t be a jump host, and no port forward can go through it.
- **Test connection**: follows the connection to the address and port and hangs up, telling you the port can be reached; it doesn’t try the automatic login.
- **Connecting**: opens a terminal tab that works like an SSH host’s remote terminal. It tells the device the terminal type (xterm-256color) and the window size, again whenever the window changes; Enter sends CR LF (PuTTY’s default). After the device disconnects (say you type `exit`), press Enter to reconnect in the same tab; changing the address, the automatic login or another setting applies to tabs opened afterwards.
- **Menus**: the tab menu has “Send break”, which sends Telnet’s break; a console server turns it into a break on its serial line. There’s no file transfer, the right sidebar has only Snippets, and there’s no system detection or latency.
- **Note**: Telnet isn’t encrypted: the username, the password and everything in the terminal travel as plain text, so use it only on networks you trust. The terminal shows UTF-8 only. When the device doesn’t take care of echo (chess servers, MUDs, or SMTP, HTTP and Redis typed at by hand), ShellRS shows what you type itself, as PuTTY does by default: the line goes when you press Enter, and until then Backspace and Ctrl+U edit it; arrow keys and the like still go straight away. The odd device that echoes without saying so shows each character twice.

**Serial hosts** are serial ports of this computer, such as a USB-to-serial cable, a development board’s debug port, or a switch’s or router’s console port. Choose “Serial” under “Protocol” in the host dialog:

- **Serial port**: type it, or pick from the menu at its right end, which lists the serial ports found on this computer; its last item, “Look again”, looks again. macOS lists only `/dev/cu.*`, Linux has paths like `/dev/ttyUSB0`, and Windows has names like `COM3`. The name is the serial port if left empty.
- **Baud rate**: 115200 by default; the menu has the common rates, and you can type any other.
- **Data bits, Parity, Stop bits, Flow control**: data bits 5–8, parity None / Odd / Even, stop bits 1 / 2, flow control None / RTS/CTS / XON/XOFF; 8N1 without flow control by default. Mark and space parity, 1.5 stop bits and DSR/DTR flow control aren’t supported.
- **Test connection**: opens the serial port with the settings you entered and closes it again, saying whether it opened, or why not (not found, in use, no permission). It only tells you this computer can open the port, not whether a device on the other end answers.
- **What it doesn’t have**: a serial host has no address, port, authentication or connection. It can’t be a jump host, and no port forward can go through it.
- **Connecting**: opens a terminal tab that works like an SSH host’s remote terminal. After it disconnects (say the USB cable is pulled), press Enter to reconnect in the same tab; changing the baud rate or another setting applies to tabs opened afterwards.
- **One at a time**: a serial port can be open in only one program at a time, and on macOS and Linux ShellRS holds it to itself. Connecting to it again while it’s open says it’s in use. On Linux, your user usually needs to be in the `dialout` group to open serial ports.
- **Menus**: a serial host’s context menu has no “Copy IP”. Hovering over it shows “device · 115200 8N1”.

**Not yet available: opening ShellRS from a bastion host’s `telnet://` link, sending files with XMODEM / YMODEM (ZMODEM works: see “ZMODEM transfers” under “Terminal”), controlling the DTR / RTS lines, and on macOS, virtual serial ports made by programs such as socat (a pseudo-terminal takes no baud rate).**

## Quick connect

“Quick connect…” at the top right of the title bar connects to a host without saving it, for machines you log in to only once. As for a new host, the dialog asks for the address, port and authentication (Password, Credential or No password); there are no Group, Connection or Notes fields, and the name is optional (the address is used instead). You can “Test connection” first. With “Telnet” as the protocol, enter the address, port and automatic login (the password stays in memory); with “Serial”, enter a serial port and its line to open it directly. “Connect” opens a terminal tab:

- **Fully featured**: “Connect in new tab”, file transfers, “Reconnect” and all the right sidebar tools work. The connection is direct.
- **Not saved**: it stays out of the host list, the start page’s Recent list and the database, and is gone once its terminal tabs are all closed. Its tab menu has no “Edit host…”.
- **Password in memory only**: the password you enter doesn’t go into the keychain and is reused when reconnecting; if you left it empty and the server wants a password, you’re asked. With “Credential”, the password or private key saved in the credential is used.

Hosts you want to keep are created with “+” at the top of the host list, the context menu, or ⌘N (Ctrl+N on Windows and Linux).

## Port forwarding

Click the port forwarding icon in the title bar and the left sidebar switches to the list of forwards. Each forwarding rule goes through a saved host and opens an SSH connection of its own when it starts, independent of that host’s terminal tabs: closing the tabs or choosing “Disconnect” on the host doesn’t affect it, and the host’s connection state doesn’t count it. While forwards are running, the number running appears next to the port forwarding icon in the title bar.

There are three kinds of forward. Think of each as “entrance → exit → destination”: a connection comes in at the entrance, goes through the SSH tunnel to the exit, and the exit connects to the destination:

| Type | Entrance (listens) | Exit | Use |
| --- | --- | --- | --- |
| Local (`ssh -L`) | This computer | Server | Reach a service on the server’s side from this computer, such as connecting a local client to a database that only the server can reach |
| Remote (`ssh -R`) | Server | This computer | Let the server’s side reach a service on this computer, such as showing someone a site you’re developing locally, or receiving webhooks |
| Dynamic (`ssh -D`) | This computer (SOCKS proxy) | Server | Use the server as a proxy, with the destination chosen by the app, such as browsing the web through the server |

- **Creating and editing**: “+” at the top of the list opens the dialog. A row of three cards at the top chooses the type; the diagram in the middle fills in the addresses as you type and marks which machine the entrance is on; and a sentence below explains what the rule does (such as “Connecting to 127.0.0.1:8080 on this computer is the same as connecting to db.internal:3306 from the SSH server.”). The “SSH server” in the diagram and the sentence is the host chosen in “Via host”; the diagram calls it by its role, not by the host’s name. A dot moves slowly along the diagram in the direction of the connection: through the SSH tunnel first, then on to the destination, pausing and starting over; switching type sends it off again from the new entrance. The name is optional; without one, the list shows a summary of the forward (`8080 → db.internal:3306`, `9000 ← localhost:3000`, `SOCKS 1080`).
- **Starting and stopping**: the button at the end of each row, double-click the row, or select it and press Enter; the context menu also has “Edit port forward…” and “Delete”. “Create” only saves the rule and doesn’t start it. Rules with “Start when ShellRS opens” checked start along with the app.
- **Status**: the end of the row shows “Connecting”, “Running” (with the current number of connections), “Connection lost, reconnecting”, or “Stopped:” with the reason. When a single connection can’t be forwarded (for example, the server can’t reach the destination), only that row says so, and the forward keeps running.
- **Login**: uses the host’s settings, the password saved in the keychain and ShellRS’s own known hosts file. A host you’re connecting to for the first time, or a password that has to be entered, brings up the same prompt as in a terminal, saying which forward is connecting; cancelling the prompt stops the forward.
- **Reconnecting after a drop**: when the connection drops, ShellRS reconnects automatically up to three times, after 1, 3 and 10 seconds. While it reconnects, the local listening port stays open, and new incoming connections are closed straight away. Automatic reconnects never prompt: if a password needs entering again or a host key needs confirming, the forward stops with the reason, and you can start it by hand. It also stops after three failed attempts, with a notification.
- **After changes**: editing a running rule’s type, host, listening address or destination restarts the forward with the new settings; changing only the name or auto start doesn’t. Editing the host it goes through (its address, authentication, credential, jump hosts and so on) leaves a running forward alone: the new settings apply the next time it starts.
- **Deleting a host**: deleting a host (or a group that contains it) also deletes the forwarding rules that go through it, stopping running ones first; the confirmation says how many.
- **Dynamic forwarding** supports SOCKS5 (no authentication, `CONNECT`, IPv4, domain names, IPv6) and SOCKS4 / 4a. Domain names are resolved by the server.
- **The listening address** defaults to `127.0.0.1`. With another address, local and dynamic forwards can be used by other devices on the same network; for a remote forward, other machines can connect only if the server’s `sshd_config` sets `GatewayPorts clientspecified` or `yes`. The default is `no`, in which case the forward still runs without an error but listens only on the server’s own `127.0.0.1` (the same as a hand-written `ssh -R`). The dialog points this out when you enter a non-loopback address. Ports below 1024 need administrator rights (root, on the server). Port 0 (letting the system pick a port) isn’t supported.

**Not implemented yet: ordering rules. The system’s “Reduce motion” setting doesn’t turn off the diagram’s animation yet.**

## Credentials

Click the credentials (key) icon in the title bar and the left sidebar switches to the list of credentials. A credential is a set of login details that several hosts can share: a name, a username and a way to log in:

| Type | What it keeps | When logging in |
| --- | --- | --- |
| Password | Username and password | Uses the password saved in the credential; asks if none is saved or it’s rejected |
| Key | Username, private key and passphrase | Uses only this private key; the passphrase is saved per key file and shared by credentials that use the same file |
| SSH Agent | Username | Uses only the keys in the SSH agent: on macOS / Linux the agent that `SSH_AUTH_SOCK` points to, on Windows the OpenSSH Authentication Agent service |

- **Creating and editing**: “+” at the top of the list, “New credential…” in the empty list, or the context menu on empty space opens the dialog; to edit a credential, double-click it, select it and press Enter, or right-click it and choose “Edit credential…”. Passwords and private key passphrases go into the system keychain; the database holds only the name, username, type and private key path.
- **Where the key comes from**: a key credential’s “Private key” has three sources.
  - **Local file**: choose a private key file, and ShellRS keeps a copy of it in `keys/` in the data folder; the original is read this once and never changed. If you change the original later (a new key, say) and can no longer connect, choose it here again. Credentials made before this version keep using the file they name.
  - **Paste**: paste a private key in OpenSSH, PEM or PuTTY format. If you paste a public key or something unrecognizable, ShellRS says why. The passphrase field appears only when the private key is encrypted with one.
  - **Generate**: choose Ed25519 (the default) or RSA 4096, and the key is generated as soon as you choose. The dialog shows the public key, with a button to copy it. The passphrase can be left empty; if you enter one, it encrypts the private key and goes into the keychain. A generated key has the credential’s name as its comment.
  - ShellRS keeps the private keys from all three sources as files in `keys/` in the data folder (with random file names, readable only by your account), and the credential refers to that file; when you edit the credential, it shows as “Local file” with that path. Pasting or generating again overwrites the file directly, and connected hosts don’t reconnect because of it; switching to another file or another type, or deleting the credential, deletes the file together with its passphrase, and the dialog warns you first. ShellRS never changes or deletes your own private key files. When the whole data folder moves (a portable copy on a new drive letter, or data copied in from elsewhere), credentials switch to the same file in its new place by themselves; the keychain knows a passphrase by the key’s path, so a key with a passphrase asks for it once more.
  - The empty list and the context menu on empty space also have “Generate key…”, which opens the same dialog with “Key · Generate” already chosen. A key credential’s context menu has “Copy public key”, for adding the public key to `~/.ssh/authorized_keys` on a server.
- **Hosts follow the credential**: changing a credential’s username changes it for every host that uses the credential. Open tabs stay as they are, and tabs opened afterwards use the new settings; the dialog says how many hosts use it.
- **Deleting**: right-click and choose “Delete”. If hosts use the credential, the confirmation says how many and how they’ll log in afterwards: hosts using a password credential switch to “Password” and ask when connecting; hosts using a key or SSH Agent credential switch to “No password”. Usernames stay the same; passwords and private keys aren’t copied over. Open connections aren’t affected, and the credential’s password is deleted from the keychain along with it.
- **An SSH Agent credential** says why right away when it can’t reach the agent, the agent has no keys, or the server accepts none of them; it never falls back to asking for a password. Hosts set to “No password” try the same agent too, skip it silently if it can’t be reached, and go on to the default private keys (on Windows as well).

**Not implemented yet: creating a credential right from the host dialog, ordering credentials, a custom SSH agent socket, installing the public key on a host automatically, and exporting the private keys ShellRS keeps.**

## Sync

Sync keeps what you save alike on your computers, through a folder, a WebDAV server or an S3 bucket: hosts, groups, credentials, port forwards and snippets, with the passwords of hosts and proxies, the passwords of credentials, the passphrases of keys and the private keys in `keys/`. The folder can be one iCloud Drive, Dropbox, OneDrive or another cloud drive syncs, or one on a network share; the WebDAV server can be Jianguoyun, Nextcloud, a Synology NAS or any other cloud drive or server that speaks WebDAV; the S3 bucket can be AWS S3’s, or one of object storage that speaks its API, such as Cloudflare R2, MinIO, Backblaze B2, Alibaba Cloud OSS or Tencent Cloud COS.

- **Turning it on**: in “Settings › Cloud sync”, click “Choose folder…” and pick a folder, or “Connect WebDAV…” and enter the server’s address, username and password. The address is the server folder sync goes in (such as `https://dav.jianguoyun.com/dav/ShellRS` on Jianguoyun), made if missing. For Jianguoyun, use an app password from “Account › Security” on its website; for Nextcloud, one from “Settings › Security”. “Test connection” writes a small file there, reads it back and deletes it, to see that sync can read and write. Or click “Connect S3…” and enter the endpoint, region, bucket, folder in the bucket and access key: an empty region is us-east-1, and Cloudflare R2’s is `auto`; tick “Path-style addresses” for MinIO and other self-hosted services; the bucket must exist already, and the access key needs only to read and write it. The WebDAV password and the S3 secret access key are kept in the system keychain only; should the server or bucket later refuse it (an app password or access key revoked, say), sync stops and asks you to sign in again, and “WebDAV login” or “S3 access key” on the settings page changes it any time. Without sync there yet, you set it up: choose a sync password (at least 12 characters, or click “Generate password”), which your other computers ask for when they join. A forgotten sync password can’t be recovered; you can only turn sync off and set it up again in another folder. With sync there already, you join it: enter its sync password, and what’s on this computer is merged with the other devices’, nobody’s deleted.
- **When it syncs**: when it’s turned on, when ShellRS starts, when its window comes forward (at most once a minute), 5 seconds after you stop editing, when you click “Sync now”, and before quitting (waiting 3 seconds at most). It never polls on a timer. A record changed on two computers keeps the later change. “Settings › Cloud sync” shows where it stands; errors show there only, with no notification.
- **What doesn’t sync**: serial hosts (the port is this computer’s), quick and external connections, the local terminals in Projects, and the settings. A host’s system, the tool its right sidebar shows, whether a group is expanded and whether a forward starts with ShellRS stay on this computer too. Keys that credentials made before this version only name by their path don’t sync; choose the key file in the credential again and it does.
- **Encryption**: everything is encrypted on this computer before it’s written to the folder or the server, which holds one file per device, ciphertext only. The sync password only unlocks the keys and is never kept; the keys are kept in the system keychain, so a computer without one can’t turn sync on. When the keychain is locked and the passwords can’t be read, a sync leaves them all as they are rather than taking them as deleted.
- **Devices**: “Other devices” lists the devices in the same folder, their system and version, and when they last synced. “Remove…” deletes that device’s file in the folder; the device asks whether to rejoin the next time it syncs. If a device is lost, remove it, then change the sync password: the data key is changed with it, so even knowing the old password, the device can’t read anything newer.
- **Changing the sync password**: the data key is changed with it. Your other devices ask for the new password when they next sync, and go on syncing once it’s entered, with nothing to merge again.
- **What waits for you**: when one sync would delete 10 records or more and over half of them, it stops first and says so in a notification and on the settings page; the records go only once you agree, and “Cancel” keeps it waiting. The same goes for sync reset on another device, or this computer removed: it waits for the password or for you to rejoin.
- **Turning it off**: what’s on this computer stays as it is; the sync keys, the WebDAV password or S3 key and the state go, and you can choose to delete this computer’s file where sync goes too.

**Not done yet: a preview of duplicate hosts when first joining, the mobile apps.**

## Settings

The “Settings” button at the bottom of the sidebar, or ⌘, (Ctrl+, on Windows and Linux), opens a “Settings” tab in the center area; if it’s already open, it switches to that tab instead of opening another. The settings page has two columns: on the left the categories (Appearance, Terminal, Highlighting, Keyboard shortcuts, Sync, General, About), with a search box at the top and a width you can drag; on the right the settings of the chosen category. Changes take effect at once and are saved in `settings.json` in the data folder.

- **Appearance → Interface → Language**: System, 简体中文 or English. The default is System: Simplified Chinese when the system language is Chinese, English for any other language. Changes apply at once, without a restart: the text in the window, open tabs and search box hints all switch to the new language; prompts already written into terminals and notifications already shown stay as they were.
- **Appearance → Interface → Appearance**: Dark, Light or System, System by default; System switches along with the system’s light and dark mode. The theme button in the title bar also changes this setting.
- **Appearance → Interface → Interface font size**: 12–20 pixels, 16 by default, or 14 on Windows (where body text is then the size of the system’s own). The interface’s text and spacing scale with it, and changes apply at once; the terminal’s font size is set separately under “Terminal → Font”. Outside a terminal, ⌘= / ⌘- (Ctrl on Windows and Linux) change it 2 pixels at a time, and ⌘0 goes back to the default.
- **Appearance → Theme**: the left column has light themes and the right column dark themes; choose one in each. The light appearance uses the one chosen on the left, the dark appearance the one on the right; with System they switch along with the system, and the same happens when you switch with the title bar’s theme button. By default only terminals take the chosen theme’s colors, and the interface stays a neutral gray (the dark one is an easy-on-the-eyes charcoal, not pure black). Turn on “Match interface to theme” at the top and the interface takes the theme’s colors too: the sidebar, tab bar, dialogs and so on use the theme’s background and text colors, and states such as success, warning and error use the theme’s green, yellow and red. Each card shows a sample in that theme’s colors, and the chosen one has a blue check mark at its top right. The defaults are ShellRS Light and ShellRS Dark, which match the interface. There are 10 built-in light themes and 10 dark ones: light ShellRS Light, Solarized Light, Tokyo Day, Catppuccin Latte, Flexoki Light, One Half Light, Gruvbox Light, Kanagawa Lotus, Rosé Pine Dawn, Everforest Light; dark ShellRS Dark, Solarized Dark, Tokyo Night, Catppuccin Mocha, Flexoki Dark, One Half Dark, Gruvbox Dark, Kanagawa Wave, Dracula, Nord. The light and dark versions of the same theme sit on the same row of the two columns. Changes apply at once to every open terminal, and the font and highlighting previews use the current theme too; when vim or another program asks the terminal for its background color, it gets the current theme’s. **Not implemented yet: custom themes, importing color schemes, and per-host themes.**
- **Terminal → Font**: Font family (lists only the monospaced fonts installed on this computer; the default is the system’s monospaced font, Menlo on macOS), Font size (10–28 pixels, default 13) and Line height (1.0–2.0 times the font size, default 1.54, the same as the earlier 20-pixel line height). Box drawing (such as the borders between tmux panes) and block characters are drawn by ShellRS to fill their cells rather than taken from the font, so they join up in every direction at any font and line height. Changes apply at once to every open terminal; in a terminal, ⌘= / ⌘- (Ctrl on Windows and Linux) also change the font size step by step, and ⌘0 goes back to the default. The preview below lays out letters, digits, easily confused characters, symbols, Chinese, box drawing and a command line the way the terminal does. If the font in the settings file isn’t installed on this computer, the default font is used.
- **Terminal → Interaction**: with “Copy on select” on, text you select with the mouse is copied to the clipboard when you let go, without pressing ⌘C; it’s off by default, and a click that selects nothing leaves the clipboard as it was. “Right-click” sets what right-clicking in a terminal does: Show menu (the default), Paste (pastes the clipboard, like ⌘V) or Do nothing. With either of the last two, the menu’s Copy, Paste, Select all, Find and Clear screen are still on their shortcuts, and Upload files, Download files and Reconnect are in the tab’s context menu. Changes apply at once to every open terminal.
- **Terminal → Sidebar tools**: two rows of icons, “In the sidebar” above and “Not shown” below, each in the sidebar’s order with the tool’s name under its icon. Click an icon, or drag it to the other row, to show or hide that tool; point at an icon to see what the tool does. All but GPU/NPU and Kubernetes are shown by default (not every host has accelerators or kubectl). “Restore defaults” at the top right of this group restores only these tools, while the page’s reset button at the top right restores the whole page. Changes apply at once: hiding the tool that’s showing collapses the right sidebar. With every tool hidden, the right sidebar and its buttons don’t appear at all, and only this setting brings them back. A tool the host’s system can’t run still doesn’t appear. Projects appears only beside local terminals, and the other tools only beside remote ones.
- **Terminal → Local terminal → Keep terminal output**: on by default; see “Projects”. Turning it off deletes all the output kept.
- **Highlighting**: the main switch, the preview and the rules table, which color text in terminals by rule and alert you on matches; see “Terminal”.
- **Keyboard shortcuts**: the shortcuts of the main features, in three groups (General, Tabs, Terminal); each row is a feature and its keys. Click the keys to get “Press a key combination”, then press a new combination to use it; Esc or clicking elsewhere cancels. The two buttons at the end of the row are Disable (the row then shows “None”; click again to restore the default) and Restore default; the “Reset All” button at the top of the page restores them all. Changes take effect at once, and the keys shown in tooltips and context menus follow.
  - A combination needs ⌘, ⌥ or ⌃ (Ctrl or Alt on Windows and Linux), or must be one of F1–F12; for “Switch to tab 1…9”, press any digit with a modifier, and all nine change together.
  - A combination already taken by another shortcut in the same place, or by text fields and other built-in features, is refused, and you’re told what uses it; to use it anyway, change or disable that one first. Terminal shortcuts can share keys with general shortcuts, and in the terminal they take precedence (in a terminal, for example, ⌘K clears the screen).
  - Defaults (macOS / Windows and Linux): New host ⌘N / Ctrl+N, New group ⌘⇧N / Ctrl+Shift+N, Open settings ⌘, / Ctrl+,, Show or hide sidebar ⌘B / Ctrl+B, Show or hide right sidebar ⌘⌥B / Ctrl+Alt+B, Show or hide compose pane ⌘⇧E / Ctrl+Shift+E, Maximize window and Restore window ⌃⌘↑ ⌃⌘↓ / none (the system’s own Win+↑ and Win+↓ do it), Show or hide ShellRS (system-wide) none, Focus search ⌘K / Ctrl+K, Zoom in, Zoom out and Actual size ⌘= ⌘- ⌘0 / Ctrl+= Ctrl+- Ctrl+0, Quit ⌘Q / Ctrl+Q; New local terminal ⌘T / Ctrl+T, Close tab ⌘W / Ctrl+Shift+W, Next tab ⌘⇧] / Ctrl+Tab, Previous tab ⌘⇧[ / Ctrl+Shift+Tab, Switch to tab 1…9 ⌘1…⌘9 / Alt+1…9 (9 is the last tab); in the terminal, Copy, Paste, Select all, Find, Find next, Find previous and Clear screen ⌘C ⌘V ⌘A ⌘F ⌘G ⌘⇧G ⌘K / Ctrl+Shift+C, Ctrl+Shift+V, Ctrl+Shift+A, Ctrl+Shift+F, F3, Shift+F3, Ctrl+Shift+K, and Bigger text, Smaller text and Default text size ⌘= ⌘- ⌘0 / Ctrl+= Ctrl+- Ctrl+0. Switching tabs stays within the group of tabs the current tab is in, wrapping around at either end. In a terminal, ⌘= / ⌘- / ⌘0 change the terminal font size (1 pixel at a time, within the same 10–28 range as “Terminal › Font size”; saved in the settings and kept for the next launch); outside a terminal they change the interface font size (2 pixels at a time, within the same 12–20 range as “Appearance › Interface font size”; saved in the settings and kept for the next launch).
  - In a terminal, a general shortcut that’s Ctrl with just a letter does nothing: the key goes to the shell as usual, such as tmux’s Ctrl+B or Ctrl+W to delete a word in bash. It works outside the terminal. So in a terminal on Windows and Linux, use the buttons for New local terminal, Show or hide sidebar and the like, or change them to Ctrl+Shift with a letter. Close tab is Ctrl+Shift+W by default (as in Windows Terminal), so it works in a terminal too.
  - “Show or hide ShellRS (system-wide)” works while another app is in front: it brings ShellRS to the front, or hides it when it’s already there (minimizes it on Windows and Linux). It has no keys until you set them, and it takes them from every app, so avoid common ones (such as ⌘Space, or ⌃Space for switching input sources). A combination another app already uses is refused, though macOS can’t always tell. No Accessibility permission is needed. On Linux it works only under X11; under Wayland, give the command that starts ShellRS a shortcut in the system settings: starting ShellRS while it runs just brings it to the front.
  - On macOS, ⌘H, ⌥⌘H and ⌘M are the menu bar’s Hide ShellRS, Hide Others and Minimize, as in other Mac apps; they aren’t on this page and can’t be given to another feature.
  - Fixed keys such as Enter, the arrow keys, Tab and Esc aren’t changed here.
- **General → Window**: “Remember window size” restores the last window size and whether it was maximized, and “Remember window position” puts the window back on the screen and in the place it last was. Both are on by default and take effect at the next launch. If that screen is gone, or the window would be mostly off screen, it opens in the middle of the screen; a window larger than the screen shrinks to fit. On a first launch (or with “Remember window size” off), if the screen has no room for the default size, say a 1920 × 1080 laptop at 150%, the window opens maximized and restores to a size that fits. Full screen isn’t remembered: the window comes back at its size from before full screen. The window’s size and position are recorded in `window.json` in the data folder as it moves. The widths you drag the sidebars to are kept in `settings.json` for the next launch; “Restore defaults” under “Sidebar widths” puts both back to their defaults (280 pixels on the left, 320 on the right), and so does the page’s reset button.
- **About**: the “Updates” group, with the current version and checking for updates, the update channel and automatic updates (see “Download and updates”); “Send anonymous usage statistics” in the “Privacy” group, on by default (see “Privacy”); and “Website” in the “ShellRS” group, which opens this project’s GitHub page in your browser.

## Opening from a bastion host (external connections)

The local client of a bastion host such as JumpServer can launch ShellRS to open a terminal the way it launches Xshell: set ShellRS as the SSH client, with the arguments written as for Xshell. When ShellRS gets an `ssh://` link, it opens a terminal tab and connects:

```sh
ShellRS ssh://user[:password]@address[:port]
ShellRS -url ssh://user[:password]@address[:port] -newtab tab-name
```

- ShellRS understands Xshell’s `-url` (the link), `-newtab` (the tab name; the address if it isn’t given) and `-newwin` (ignored: ShellRS has only one window), in any letter case; other options are ignored. Only `ssh://` is supported, and the port defaults to 22. Special characters in the username and password can be escaped by URL rules (`@` as `%40`); a username that itself contains `@` also works, since only what follows the last `@` is the address.
- **The tab fills the window**: when an external connection opens, the host list on the left collapses automatically (as with ⌘B); double-click the tab to show it again, or press ⌘B on macOS (on Windows and Linux, Ctrl+B in a terminal goes to the shell).
- **External connection, not saved**: it stays out of the host list, the start page’s Recent list and the database, and is gone once its terminal tabs are all closed. Its tab menu has no “Edit host…”; everything else (“Connect in new tab”, “Reconnect”) works as for a saved host.
- **One channel only**: many bastion hosts end the whole session when a second channel opens on the same connection. A terminal doesn’t detect the host’s system (its tab shows the first letter of the name), and the right sidebar has only Snippets: History, tmux, Docker, Services, Processes, Network, Monitor and GPU/NPU all need another channel, so they aren’t offered here.
- The password in the link stays only in memory, never in the keychain, and is reused when reconnecting; if the link has no password and the server wants one, you’re asked. The first time you connect to a bastion host, you trust its host key, which is recorded in ShellRS’s own `known_hosts` and not asked about again.
- When ShellRS is already running, the link goes to the running ShellRS, its window comes to the front, and no second ShellRS starts. If the link has a problem (not `ssh://`, no username or address, a wrong port), ShellRS shows a notification saying why.
- The program for the bastion host to launch:
  - Windows: `shellrs.exe` in the installation folder (by default `%LOCALAPPDATA%\Programs\ShellRS\shellrs.exe`), or in the portable folder for the portable copy.
  - macOS: `/Applications/ShellRS.app/Contents/MacOS/shellrs`. Don’t use `open -a ShellRS --args …`: when ShellRS is already running, the system drops the arguments.
  - Linux: the AppImage itself.
- A password in command-line arguments is visible in this computer’s process list; that comes with how the bastion host passes arguments.

## Tabs

Remote terminal tabs use the host’s system badge as their icon: the host list’s when the tab opens, and for a terminal what its own connection then finds; a system another connection finds later updates only the host list. A serial host’s terminal tab menu has no “Upload files…”, “Download files…” or “Copy IP”, and has “Send break” instead: it holds the line in the break condition for about 0.3 seconds, as Cisco password recovery and Linux’s SysRq need. A Telnet host’s tab menu has “Send break” too (sending Telnet’s break) and “Copy IP”, but no “Upload files…” or “Download files…”. A remote terminal tab’s context menu has “Rename tab…” (for this run only; leave the name empty to go back to the host’s name; handy for telling several connections to the same host apart), “Connect in new tab”, “Upload files…”, “Download files…”, “Copy IP” / “Copy hostname”, “Reconnect”, “Edit host…”, and “Close”, “Close to the left”, “Close to the right”, “Close others” and “Close all”. The right of an SSH host’s terminal tab bar has “Upload files…”, “Download files…” and “Reconnect” buttons (see “File transfer”); a local terminal tab’s menu has “Restart” and the close commands. The “…” button at the right of the tab bar has the same menu as the current tab’s context menu. Double-click any tab’s title to hide or show the left sidebar (like ⌘B and the title bar button); middle-click it to close the tab, as × does; double-click the empty space to the right of the tabs to open a new local terminal. When there are more tabs than fit, turn the mouse wheel over the tab bar to scroll them. While a remote terminal is running, the right of the tab bar shows the round-trip latency of that SSH connection, updated every 5 seconds: green below 100 ms, yellow at 100–200 ms, red above 200 ms or on a timeout. It’s measured during file transfers too, and the reading rises when a transfer takes up the bandwidth.

### Compose pane

For writing and editing commands, several lines if you like, before sending them to a terminal. ⌘⇧E (Ctrl+Shift+E on Windows and Linux) or “Compose pane” in the terminal’s context menu shows or hides it. It sits below the terminals, between the sidebars; there’s one for the whole window, and you can drag its top edge to change its height.

- **Where it sends**: to the terminal in front, local or remote, the same one the right sidebar and the status bar follow (in a split, the terminal you last switched to or clicked into). Its title says which, such as “Compose · web-01”. With no terminal on screen it hides, and comes back with the next one.
- **Sending**: press Enter or click “Send” to run what you wrote; Shift+Enter starts a new line. It’s sent as it is, after whatever is already typed in the terminal; the line isn’t cleared first. Several lines are pasted as one and then run when the terminal supports bracketed paste (zsh, fish, bash 5.1 and later by default), and run line by line otherwise. Once sent, the pane is empty again and keeps the keyboard; Enter in an empty pane presses Enter in the terminal. A terminal running a full-screen program (vim, top and so on) gets no command, and a notification says so.
- **History**: ↑ on the first line goes back to the commands sent before, as in a terminal; ↓ on the last line goes forward again, and past the newest back to what you were writing. Several lines are one command: going back to one puts the caret on its first line, so ↑ goes on at once; on the other lines ↑ and ↓ move the caret as usual. You can change a command you went back to before sending it, and the change stays until you next send. Commands that are empty, the same as the one before or start with a space aren’t kept (as with bash’s `HISTCONTROL=ignoreboth`), and neither are those sent from “Snippets”. The last 500 are kept as plain text in `compose-history.json` in the data folder, so they’re there at the next launch; they aren’t synced.
- “Snippets” sends a snippet, run or only put on the input line as its “Run on click” setting says. “Ctrl+C” sends Ctrl+C to the terminal.
- Whether it’s shown is kept for the next launch; its height and anything not yet sent are kept until you quit.

### Broadcast input

For running the same commands on several hosts at once. Click “Broadcast input” at the left end of the tab bar, beside the sidebar button: remote and local terminal tabs show a checkbox ahead of their icon, all unchecked; the icon still shows whether the terminal is connected. Only connected terminals can be checked.

- Once two or more are checked, they’re arranged side by side in the order checked: two next to each other, three or four in two rows of two, and so on. The compose pane appears below them (or stays, if it was already open) and sends to all checked terminals. Checking another arranges them again; unchecking one only takes it out of the broadcast and leaves the layout alone.
- **Compose pane**: while broadcasting it’s the command bar, and its title says “N checked terminals”. Press Enter or click “Send to all” to run what you wrote in every checked terminal; it’s sent as it is, and the line isn’t cleared first (as with Xshell’s and SecureCRT’s sending to all sessions). “Snippets” and “Ctrl+C” go to all of them too, and a “Sync keys” switch appears. A terminal running a full-screen program gets no command, and a notification says which. While broadcasting, the compose pane can’t be hidden; ⌘⇧E only moves the keyboard to it.
- **Sync keys**: off by default. Turned on, what you type or paste in one checked terminal goes to the others too, each handling arrow keys and bracketed paste in its own mode, which works in full-screen programs such as vim as well. A password you type goes along too.
- Search fields, authentication dialogs, mouse actions, terminal protocol replies, and commands from History or the Snippets sidebar aren’t broadcast. A broadcast Ctrl+C cancels a ZMODEM transfer running in another terminal; with Sync keys on, your keys stop another Telnet terminal’s automatic login.
- A terminal that’s closed, disconnected or reconnected leaves the broadcast; check it again after reconnecting. New terminals aren’t checked by themselves. Click × at the top right of the compose pane, or “Broadcast input” again, to stop: the checkboxes go away, the compose pane goes back to how it was before (hidden, if it wasn’t open), and the split layout stays for you to drag back. Broadcasting isn’t saved.

## Terminal

Remote terminal tabs show their own connection state: the icon is in color when connected; while connecting and when disconnected, the icon turns gray and so does the tab’s name. Hover over the icon to see the state in words (such as “Ubuntu · Not connected”). After a remote connection fails, exits, is disconnected or has authentication cancelled, the terminal says “Press Enter to reconnect or Space to close the tab”: with the terminal focused, an unmodified Enter reconnects that tab with the settings it opened with, and Space closes the tab (like its ×). Held keys, pasted input, search fields and authentication fields do not trigger either. Local terminals retain their restart action.

The terminal’s context menu has “Copy”, “Paste”, “Select all”, “Find…”, “Clear screen” and “Compose pane”; a remote terminal’s also has “Copy IP” (“Copy hostname” when the address is a domain name) and “Copy ID” below “Copy”, and “Upload files…”, “Download files…”, “Reconnect” and “Disconnect” at the bottom. “Disconnect” disconnects only this tab: the tab stays and can reconnect at any time, and other tabs for the same host aren’t affected. Settings › Terminal › Interaction can make right-click paste or do nothing instead, and can turn on “Copy on select”.

- **Scrollback**: each terminal keeps the last 10,000 lines. Scroll up with the wheel or trackpad and a scrollbar appears on the right (as in the app’s other lists, following the system’s “Show scroll bars” setting); drag it, or click the track to jump there. Full-screen programs such as vim, less and top have no scrollback and show no scrollbar.
- **Select all** (⌘A, or Ctrl+Shift+A on Windows and Linux): selects all the text in the scrollback and on the screen, leaving out blank lines before and after it; press ⌘C (Ctrl+Shift+C) to copy it. With “Copy on select” on, it goes straight to the clipboard. While a full-screen program such as vim or less is running, only the screen is selected.
- **Find** (⌘F, or Ctrl+Shift+F on Windows and Linux): opens the find bar at the top right of the terminal and searches the screen and the scrollback for the literal text. An all-lowercase query ignores case; one with capital letters matches case. All matches are highlighted, the current one darker, and the find bar shows “current/total”. Enter or ⌘G (F3) goes to the next match (newer output), Shift+Enter or ⌘⇧G (Shift+F3) to the previous one (older output), wrapping around at the ends. Esc closes it. If text is selected when it opens, that text becomes the query.
- **Clear screen** (⌘K, or Ctrl+Shift+K on Windows and Linux; when the terminal doesn’t have focus, ⌘K still focuses the sidebar’s search box): clears the screen and the scrollback, leaving only the prompt line the cursor is on, including anything typed but not yet entered. Clearing happens only locally; nothing is sent to the server. It isn’t available while a full-screen program such as vim or top is running.
- **Links**: `http://` and `https://` addresses in the output, and links that programs mark explicitly (such as `ls --hyperlink` and gcc’s error messages), are shown in blue and underlined. Hold ⌘ (Ctrl on Windows and Linux) and click to open one in the system browser; a plain click still selects text. Rest the pointer on a link for a moment to see its real address: for a link a program marks, the text shown can differ from the address. A trailing period, comma or unmatched closing parenthesis isn’t part of the address, and a long address wrapped over two lines is still one link. Other schemes (such as `file://`) aren’t treated as links.
- **Mouse**: when programs such as vim (`:set mouse=a`), htop, tmux (`set -g mouse on`) and mc ask for the mouse, clicks, drags and the scroll wheel all go to the program. Dragging with Shift held still selects text, and scrolling with Shift held still scrolls through the scrollback; right-clicks never go to the program and do what “Right-click” in the settings says.
- **Notifications**: programs can ask for a notification (OSC 9, or OSC 777’s `notify;title;body`), and a terminal bell alerts you too. When ShellRS isn’t in front, you get a system notification (macOS asks for permission the first time), and clicking it takes you back to that terminal; when ShellRS is in front but the terminal is in another tab, a notice appears at the top right of the window, and clicking it switches there. Notifications that programs ask for appear even when the terminal is right in front of you; the bell alerts you only when you can’t see that terminal (Tab completion and the like ring it too; a terminal shown in a split counts as seen). The notification title is the tab name, so you can tell which host it came from. Each terminal alerts at most once every 2 seconds for program notifications and once every 10 seconds for the bell. Settings › Terminal › Notifications can turn each one off. To be told when a command finishes, append `; printf '\e]9;Done\a'` or `; tput bel` to it; command-line tools such as Claude Code alert you the same way when they need you.
- **Highlighting**: the rules in Settings › Highlighting show matching text in the rule’s color in every terminal, scrollback included. Only the display changes: the server’s output and copied text stay the same; matching keeps working after the window is resized and long lines wrap, and a word wrapped over two lines is colored in both parts. The feature is off by default and works only once you turn on “Highlight keywords” at the top of the page; turning it off disables all the rules at once. “Preview” shows sample output in the current terminal’s font and colors, and rule changes show up at once in the preview and in open terminals. The rules table has one rule per row, edited right in the table: “On”, “Regular expression” (case-sensitive; start it with `(?i)` to ignore case), “Note”, a color (click the swatch for a color picker, or type `#rrggbb` next to it) and “Notify”; the trash can at the end of the row deletes the rule. A mistake in a regular expression is pointed out below the field, and the rule doesn’t apply until it’s fixed. Rules apply from top to bottom, and where they overlap, the earlier rule wins; drag the handle at the start of a row to reorder. Three sample rules come to start with: `ERROR` in red, `WARN` in amber and IPv4 addresses in blue, all on and not notifying, so turning on the main switch shows the effect right away; you can change or delete them. A rule with “Notify” checked alerts you when you can’t see the terminal, the same way as the bell: a system notification when ShellRS isn’t in front, and a notice at the top right of the window when the terminal is in another tab. The title is “tab name: note” (the regular expression when the note is empty), and the body is the matching line. Only new output is checked, each line once it ends; each terminal alerts at most once every 10 seconds, and the same line redrawn over and over at most once every 5 minutes. Nothing is highlighted or alerted in full-screen programs such as vim, less, top and tmux. **Not implemented yet: per-host rules, text styles such as bold, and reordering with the keyboard.**
- **Remote copy**: what remote programs copy with OSC 52 (such as tmux with `set -g set-clipboard on`, or vim’s OSC 52 plugins) goes straight to this computer’s clipboard. Remote programs can’t read this computer’s clipboard.
- **Shift+Enter for a new line**: command-line tools such as Claude Code ask whether the terminal can tell keys apart (the kitty keyboard protocol). ShellRS says it can and, while they run, sends keys the way the protocol asks, so Shift+Enter starts a new line in them (Option+Enter, or Alt+Enter on Windows and Linux, still works too); in remote terminals as well. In a plain shell, Shift+Enter is still Enter.
- **Local terminal tab names**: a local terminal’s tab shows the title its shell sets. Until it sets one, a terminal kept in Projects shows its last title or its name there, and others a name such as “Local terminal 1”. A terminal you named yourself in Projects always shows that name. zsh and bash often set it to “user@host:folder”; when that’s this computer and the title is longer than 30 characters, the tab shows just the folder’s name (such as `go-dock`). A shorter title, or one from another machine you ssh to from it, shows as it is. While a program runs, the tab shows the title the program sets, such as “✳ Claude Code”. A tab name that’s too long ends in “…”.
- **ZMODEM transfers**: run `rz` or `sz file…` in a terminal (the server needs lrzsz, such as `apt install lrzsz` or `yum install lrzsz`) and ShellRS takes it up. It works in SSH, Telnet and serial terminals, on a bastion host that gives you only a shell, and in a local terminal where you ssh on to another machine.
  - `rz` opens a picker for the files to upload (you can choose several). `sz` opens a picker for the folder to save into, every time. Cancelling the picker stops `rz` or `sz` on the other end.
  - Drag and drop: drag files from the Finder (File Explorer) onto a remote terminal, and ShellRS types `rz` and Enter for you and uploads them without asking. Folders you drag along are left out; upload folders with “Upload files…” at the right of the tab bar.
  - During a transfer, a line in the terminal shows the progress (file name, percentage, size, speed), and each file leaves a line when it’s done. Press Ctrl+C to cancel; other keys do nothing meanwhile.
  - A download never overwrites a file: one with the same name is saved as “name (1)”, and a file not received in full is deleted. lrzsz’s `rz` doesn’t overwrite a file of the same name on the server either and shows “Skipped”; use `rz -y` to overwrite.
  - After you cancel a download, lrzsz’s `sz` sends on for a moment before it stops; ShellRS doesn’t show that data, and shows the prompt once it has stopped. Press Ctrl+C again to stop waiting.
  - A file can be at most 4 GB, the limit of the ZMODEM protocol. It doesn’t work inside tmux or screen, which change the data on its way. Over Telnet, the server has to handle carriage returns the way Telnet says (most do).
- **Without a graphics card**: in a virtual machine without 3D acceleration, the processor draws the interface (the version number’s tooltip on the About page says “software rendering”), and every frame costs processor time. ShellRS then draws fewer frames: terminal output at most every 50 milliseconds (the first after a pause still at once, so typing isn’t affected), a cursor that doesn’t blink, and no animations. If the virtual machine can turn on 3D acceleration, turn it on.

## Right sidebar

When the current tab is a remote terminal, a column of tool buttons runs down the right edge of the window: Snippets, History, tmux, Docker, Kubernetes, Services, Processes, Network, Monitor and GPU/NPU, of which Kubernetes and GPU/NPU aren’t shown by default; choose which tools it shows in Settings › Terminal › Sidebar tools. Click one to open that tool on the right, and click it again to collapse it; ⌘⌥B (Ctrl+Alt+B on Windows and Linux) shows or hides the right sidebar. Drag the right sidebar’s left edge to resize it: it’s 320 pixels wide by default and can go down to 220, and the next launch keeps the width. When the current tab is a local terminal, the column has two buttons: Projects (see Projects below) and Snippets. The right sidebar appears only with terminals: switching to Settings hides it together with its buttons. Whether it’s open, and which tool it shows, is remembered for each host: switching to a host’s terminal brings it back as that host last had it, and a host you haven’t opened it for has it collapsed. Saved hosts remember it the next time you start ShellRS; quick connections only until you quit. For example, open Monitor on web-01 and it opens by itself whenever you connect to web-01, but not for other hosts. Local terminals share one such setting, also remembered next time. With tabs dragged into a split, the right sidebar stays: it goes with the terminal, remote or local, you switched to or clicked into last, and hides only when no terminal is on screen. Its title names the host it works on (such as “Monitor · web-01”), and the status bar follows the half you clicked into too. Hosts known not to run Linux (macOS, Windows, BSD) don’t show the Services, Processes, Network, Monitor and GPU/NPU icons; History, tmux, Docker and Kubernetes are there for every host except Windows ones (on a Mac, they work too with tmux or Docker Desktop installed). Telnet and serial terminals have only Snippets: the other tools run commands beside the terminal, which Telnet and a serial line can’t.

**Snippets** keeps the commands you use often, shared by every host and local terminal, beside remote and local terminals alike. Click the plus at the top to create a snippet: a name, a category and a command, which can span several lines. The list works like the host list: categories can nest to any depth, each level lists its categories and then its snippets, and snippets without a category sit at the top level after the categories. Each row shows only the name; hover over a snippet to see its command beside it. Click a category to collapse or expand it (this isn’t remembered: categories are expanded at the next launch). Right-click a category to create a snippet or a subcategory in it, rename it or delete it (its subcategories and snippets are deleted with it, and the confirmation says how many). The folder button at the top creates a top-level category; when you rename a category, you can also choose a “Parent category” to move it. Two categories at the same level can’t share a name; at different levels they can.

Drag rows to rearrange them: drop a snippet on the upper or lower half of another to put it before or after it (in that snippet’s category), or on a category to put it last in that category. Drop a category on the top or bottom edge of another to reorder them, or on its middle to make it a subcategory. Drop anything on empty space to move it to the end of the top level. A category can’t go inside itself or one of its own subcategories, and rows can’t be dragged while you search. New snippets and categories go last at their level; ones from earlier versions that were never dragged stay in name order. Order and nesting sync with cloud sync; ShellRS 0.1.17 and earlier show every category at the top level, but don’t change the order or nesting elsewhere. You can search by name or command; with several words, snippets that contain all of them are listed, with the categories they’re in.

Clicking a snippet runs its command in the terminal (snippets are set to “Run on click” by default). When the pointer is on a snippet, an icon at its right shows what a click will do: a lightning bolt means a click runs it, ▶ means a click only types it in. Uncheck “Run on click” in the snippet dialog, and clicking the snippet only puts the command on the terminal’s input line (replacing anything already typed), for you to edit and press Enter. Clicking the lightning bolt or ▶ at the right always runs it right away; the context menu also has “Insert into terminal”, “Copy command”, “Edit…” and “Delete…”. Nothing is typed in while a full-screen program such as vim or less is running in the terminal. On Windows hosts, and in local terminals on a Windows computer, what’s already typed isn’t replaced; the command is typed after it.

**History** lists the remote host’s bash history (`~/.bash_history`), most recent first, each command once, with how many times it ran below it; when bash recorded times (`HISTTIMEFORMAT` is set), it also says when it last ran, and multi-line commands are recognized. You can search; with several words, commands that contain all of them are listed, ignoring case. Click a command to put it on the terminal’s input line (replacing anything already typed, without running it), for you to edit and press Enter; the “Run” button at the right runs it right away, and the context menu can also copy it. Nothing is typed in while a full-screen program such as vim or less is running in the terminal.

bash writes a session’s commands to the history file only when the shell exits, so commands you’ve just run in the current terminal show up only after it exits. The list is read when you open History or switch terminals, and after that only when you click the refresh button; when the history file is long, only its last 512 KB is read.

**tmux** lists the remote host’s tmux sessions: the name, how many terminals are attached (“N attached” or “Detached”) and the folder the session started in, with the session the current terminal is in marked “Current”. The tmux version is at the top; a host without tmux says “tmux isn’t installed on the host”, and the buttons don’t work. “New” asks for a name (leave it empty for tmux to number it; letters, digits, - and _ only), then puts the current terminal in the new session; “Detach” takes the terminal out of its session, which keeps running. Each session has “Attach” (puts the current terminal in that session), “Rename” and “End session” (asks first; every program running in the session ends) at the right.

When the current terminal isn’t in tmux, attaching and starting a session type `tmux attach -t name` or `tmux new -s name` into the terminal and run it (as History does, in place of what’s typed there; nothing is typed while a full-screen program such as vim runs). When the terminal is in tmux already, what’s typed goes to the program in the tmux pane, so tmux is told over the terminal’s connection to switch the terminal instead, and nothing is typed. ShellRS finds the terminal’s tty from the SSH connection’s sshd and matches it against tmux’s clients to tell whether the terminal is in tmux and in which session; when it can’t (a server without `ps`, say), the terminal counts as not in tmux. Only the login user’s own sessions are listed: tmux sessions started after `sudo -i` in the terminal aren’t here. The list is read when you open tmux or switch terminals, again after attaching, starting, renaming, ending and detaching, and otherwise when you click the refresh button.

**Docker** shows the Docker and Compose versions at the top, and below them four tabs with counts: “Containers”, “Volumes”, “Images” and “Networks”. On “Containers”, the containers of the same compose project are grouped under a project card (project name, running / total, project folder); click the project’s row to collapse or expand it. A project with a single container that’s running starts expanded, and a project with several containers starts collapsed; containers that belong to no project are under “Standalone containers”. Each project and container has “Stop” (or “Start”) and “Restart” at the right, and a project’s buttons act on all its containers. Click a container or its “…” to open its details: the “Details” tab has the name, ID, image, creation time, entrypoint, command, ports, mounts, environment and labels, and the “Logs” tab the container’s last 200 lines of output; at the bottom you can start, stop and restart it, and delete it once it’s stopped. The “Volumes”, “Images” and “Networks” tabs list each item’s name and basic information and mark whether a container uses it; those no container uses can be deleted with the delete button at the right (Docker’s own bridge, host and none networks can’t be deleted). Click a card to open its details: for a volume, the driver, mountpoint, creation time, the containers using it, options and labels; for an image, the full ID, tags, digests, creation time, size, platform, number of layers, the containers using it, configuration (entrypoint, command, working directory, user, exposed ports), environment and labels; for a network, the driver, scope, IPv6, subnets and gateways, the containers attached with their addresses, options and labels. Items can be deleted from the bottom of the details too.

Stopping, restarting and deleting ask first; starting happens right away. The result appears as a notification, and the list is read again. When you’re not logged in as root and not in the docker group, passwordless sudo is used. The list is read when you open Docker or switch terminals, and after that only when you click the refresh button. If Docker isn’t installed or isn’t running on the host, it says so.

**Services** lists the systemd services on the remote host (not templates) in two groups: “Custom services” (unit files in `/etc/systemd/system`, the ones an administrator added) and “System services”. The top shows the systemd version and the overall state of the machine (“Degraded” when a service has failed); there are four tabs with counts, “All”, “Active”, “Inactive” and “Failed”, and you can search by service name or description. Each service has a card: a status dot, the name, description, active state and whether it starts at boot. A running service has “Stop” and “Restart” at the right, one that isn’t running has “Start”, and “…” or clicking the card opens its details. The details’ “Status” tab has the load state, active state, at boot, main PID, memory, tasks, restarts, exit status, start and stop times, and unit file; the “Journal” tab has the service’s last 200 lines in the journal. At the bottom of the details and in the context menu you can likewise start, stop and restart it, and enable or disable it at boot.

Stopping and restarting ask first (with a special warning when you stop the SSH service); starting and the at-boot setting happen right away. The result appears as a notification, and the list is read again. These actions need root: when you’re not logged in as root, they run through passwordless sudo, and if sudo needs a password, you’re told that root is needed. The list is read when you open Services or switch terminals, and after that only when you click the refresh button. For hosts that don’t use systemd, it says they’re not supported yet.

**Processes** lists the processes on a remote Linux host (without kernel threads), each on a card: a status dot (green running, gray sleeping, yellow waiting for I/O or stopped, red zombie; hover over it to see the state), the process name, PID, user, start time (in this computer’s time zone), memory use with its share of physical memory, and CPU usage. CPU usage is computed the way `top` does it, per core: two full cores is 200%. It takes two readings to compute, so right after the tool opens it shows “—”, and the figure appears 2 seconds later. Processes are sorted by memory, most first, by default; click “CPU” to sort by CPU instead, and click the same button again to reverse the order. You can search by process name, PID or user, and the number at the right is how many are listed. The list refreshes every 15 seconds, reading only while Processes is showing; click the refresh button at the top right to read it at once.

Click a process to open its details: PID, parent, user, state (with the `ps` state letters in parentheses, such as `Ssl`), start time, elapsed time, TTY, priority, nice, CPU usage, CPU time, resident memory, virtual memory, number of threads, of direct children and of all descendants, and below them the full command line (read when the details open; “Copy command” copies it). At the bottom are “Copy PID”, “End process” and “Kill”.

Right-click a process for “View details”, “End process…” (sends SIGTERM, so the process can clean up before it exits) or “Kill process…” (sends SIGKILL, ending it immediately); ending it from the details works the same way, and both ask first. The result appears as a notification, and the list is read again 1 second later. When you’re not logged in as root, you can end only your own processes. With more than 2500 processes, only the first 2500 are listed, and the top of the list says so.

**Network** lists every TCP and UDP connection and listening port on a remote Linux host, each on a card: protocol, state, local and remote addresses, the process using it with its PID, and its user. The top right of each card says whether it’s a “Listening port”, “Inbound” (connected to a port this host listens on) or “Outbound”. The top of the panel shows the total, the number of listening ports and the number established; you can search by address, port, state, PID, process name or user, and filter by protocol and state. Listening sockets come first, then established ones, with TIME_WAIT and other closing ones last; when several processes listen on the same port together (such as nginx’s workers), they’re merged into one card.

The list is read once when you open Network or switch terminals and doesn’t change by itself after that; click the refresh button at the top right to read it again. The data is read over this terminal’s existing SSH connection, with no second login, using the host’s `ss` command; on hosts without `ss` (such as BusyBox) it’s read from `/proc/net` instead, and then processes don’t show; when you’re not logged in as root, you see only your own processes. In both cases the top of the list says so. With more than 3000 connections, only the first 3000 are listed (listening ports are always among them), and the total stays accurate.

**Monitor** shows, for a remote Linux host:

- **System**: host name, architecture, distribution and uptime (such as “32 days 23:40:26”).
- **CPU**: model, number of cores and average usage; with several cores, a small bar for each core below, and hovering over a bar shows that core’s number and usage. Only one row shows by default; when there are too many cores for one row, click “N cores” at the top right to show them all.
- **Memory**: physical memory usage and the amount used; a second row when there’s swap.
- **Network**: upload and download rates of the main interface (the one with the default route); with several interfaces, click “N interfaces” at the top right to show them all (loopback interfaces and interfaces that have never sent or received data aren’t listed).
- **Disks**: the usage of each local mount point (without in-memory file systems such as tmpfs, or mounts under system folders).

The data is read over this terminal’s existing SSH connection, with no second login and nothing to install; it refreshes every 2 seconds (disks every 30 seconds), reading only while Monitor is showing. Each refresh reads only a few system files, and starts no processes on the server besides the shell that runs it. Usage of 70% or more shows in yellow, 90% or more in red. When the terminal isn’t connected, it says so; when a host whose system wasn’t known yet turns out not to be Linux, it says it isn’t supported yet.

**GPU/NPU** is for looking after AI hosts: it shows a remote Linux host’s NVIDIA GPUs (read with `nvidia-smi`) and Huawei Ascend NPUs (read with `npu-smi info`). It isn’t shown by default; turn it on first in Settings › Terminal › Sidebar tools. It’s laid out for hosts with eight:

- **Summary**: the model and driver version, the number of devices and how long the host has been up, and over all devices the average utilization, memory (how full, with used / total under it), the highest temperature and the total power.
- **Devices**: three lines a device. The first has its number (GPU 0, NPU 3; a card with more than one chip lists each, as NPU 0.1), model, temperature and power; the next two have its usage and memory bars, the same length so they compare. Click a device to unfold its details: model, UUID, bus ID, performance state, power and its limit, fan (when it has a reading) and health; “Expand all” and “Collapse all” at the top right do every device at once. A host with one device shows it unfolded.
- **Compute processes**: the processes computing on the devices, by device, the most memory first on each; each with its command line, memory, device, PID and user. A process `ps` can’t see (in another PID namespace) has only its program name. Right-click one to “End process…” or “Kill process…”, as in Processes; both ask first.

A figure that can’t be read shows as “—”, not 0. Utilization and memory aren’t colored by how full they are: a GPU at 100% while training, or memory taken up front by an inference server, is how they should run. Temperatures of 80 °C or more show in yellow, 90 °C or more in red; a device in poor health (uncorrectable ECC errors on NVIDIA, an Ascend Health other than OK) has a yellow or red dot beside its number, and pointing at it says why. When `nvidia-smi` or `npu-smi` fails (a GPU fell off the bus, the driver isn’t loaded, no permission), what it said shows as it said it.

The data is read over this terminal’s existing SSH connection, with no second login and nothing to install; it refreshes every 2 seconds (counted from the end of the last reading, so a slow `npu-smi` slows it down), the uptime with it, reading only while GPU/NPU is showing. Each tool gets 3 seconds; one that doesn’t answer is stopped, and so is reading until you click the refresh button: a failing GPU can leave `nvidia-smi` stuck in the driver, and retrying would pile up stuck processes on the server. A host with neither tool says so. **Not supported yet: AMD, Hygon DCU, Cambricon and other vendors.**

### Kubernetes

The Kubernetes sidebar uses `kubectl` and kubeconfig on the SSH host, over the terminal's existing connection. The host needs POSIX `sh`, kubectl, a current context and cluster read permissions. The tool is hidden for Windows hosts and external connections restricted to a single channel. It isn’t shown by default: turn it on in Settings › Terminal › Sidebar tools. Turning it off hides it and stops reading lists, logs and performance.

Select a context, then choose from all discovered namespaces or use “All namespaces”. Browse nodes, workloads, services, configuration and storage, including HPA, PDB and EndpointSlice resources. Search filters names, namespaces, status and labels in the loaded list. Open a resource to inspect its properties and syntax-highlighted YAML. Detail values support native text selection and copying. Secret lists and details read metadata only. Workloads link to pods in the same namespace after verifying ownership and UID; the relationship view lets you navigate controllers, containers and configuration references. The overview's related-pod list is independent of the diagram's 160-node display limit.

YAML editing, workload or managed-pod restarts, and deletion require confirmation that identifies the context and exact resource. Writes include UID and resourceVersion checks; failures retain the draft. Secrets cannot be edited. Node and pod performance tabs query optional Metrics API data only while visible; node disk readings use the kubelet Summary API. Missing permissions or metrics are shown without hiding resource details. Memory uses GiB-scale G units; displayed resource and log timestamps use UTC+08:00 while YAML and copied raw logs retain their original values.

In a pod's Logs tab, choose a regular, init or ephemeral container, the last 100–10000 lines and a time range from 5 minutes to 24 hours. “Previous container” reads the selected container's previous instance. Search is case-sensitive, supports regular expressions and shows matched line counts. Logs highlight timestamps, levels and JSON fields; copy individual lines or search results. “Live preview (2 s)” refreshes the latest retrieved window with serial requests. The buffer is capped at 512 KB / 10000 lines; long lines display up to 16 KB while search and copy use the full buffered text. Turn off auto-scroll to read earlier lines. Refreshing stops when leaving Logs, closing details or encountering a query error. Commands offers continuous `--follow` in the terminal.

Commands also generates describe, YAML, logs and `/bin/sh` exec commands, explicitly scoped to the selected context, namespace, resource and container. Copy them into a terminal on the same SSH host. Browsing does not modify kubeconfig or cluster resources. Lists are read when opened, on a change of terminal or scope, after a change made here and on Refresh; they don’t refresh themselves. Structured reads use API pagination and optional gzip/base64 compression, with a 1 MB SSH response limit, 16 MB decompression limit and 64 MB / 100000-item list limit. Permission failures and incomplete responses are displayed; namespace access denial never appears as an empty successful discovery.

### Projects

Beside local terminals, the right sidebar has Projects and Snippets (the same Snippets as beside remote terminals; see above). Projects keeps local terminals as hosts are kept, in groups if you like. For example, make a group “shellrs” and open one terminal in it for Claude Code and another for `cargo run`. Each terminal remembers the folder its shell was last in, and those open when you quit ShellRS come back in their folders at the next launch.

- **New local terminals**: the plus button on the sidebar’s title bar, right of “Projects” and left of “…”, or the menu of the blank space, opens a terminal of no group; the plus button at the right of a group’s row, or New local terminal in a group’s menu, opens one in that group. Nothing to fill in: it opens at once, numbered (shellrs 1, shellrs 2… in a group, Terminal 1, Terminal 2… outside one). Its name in the list and on its tab follows the title the shell or a program sets, such as “✳ Claude Code” while Claude Code runs. After you close its tab or quit ShellRS, the last title still shows, and it shows again when the terminal reopens, until the shell or a program sets a new one. The numbered name shows only if nothing has ever set a title. Choose Rename… in its menu to give it a name you’ll recognize: that name then always shows, whatever the title. Leave the name empty to follow the title again. A new terminal in a group starts in the folder the group’s last terminal was in; others start in your home folder.
- **Groups**: the folder button beside the plus button, New group in the empty list, or the menu of the blank space; a group has only a name, such as work. Groups don’t nest, and two can’t share a name. Right-click a group to rename or delete it; deleting a group deletes the terminals in it too, closing the tabs of those open, after asking.
- **The list**: as in the host list, groups come first and terminals of no group after them all. A group’s row is its name; a terminal’s is two lines, its name and below it the folder it was last in (your home folder written as `~`); hovering shows the full path. Open terminals have a green icon, closed ones a grey one. Click an open terminal to bring its tab to the front; click a closed one to open it again in the folder it was last in (or your home folder if that folder is gone). Click a group’s row to fold or unfold it; as in the host list, it stays that way at the next launch.
- **Dragging into order**: drag rows as in the host list. Drop a group on the top or bottom half of another to put it before or after it. Drop a terminal on the top or bottom half of another terminal, in its group or another, to put it before or after it, on a group to put it last in that group, or on the blank space below the list to take it out of its group, last.
- **Closing and deleting**: closing a terminal’s tab (or choosing Close in its menu) leaves it in its group, grey, to open again with a click. To get rid of it, click the delete button that appears at the right of its row while the pointer is on it, or choose Delete in its menu. A terminal that isn’t open goes at once, without asking; one that’s open asks first, then its tab closes with it, ending what runs in it. Restart starts a terminal again in the folder it was last in, with the shell set now.
- **Remembering the folder**: wherever you `cd` in the terminal, ShellRS remembers it, by reading the shell’s own current folder, with no shell setup. This works on macOS and Linux; on Windows it can’t be read, and terminals there always start in your home folder. Programs running in the terminal, such as Claude Code, don’t change the folder remembered.
- **Reopening at the next launch**: which Projects terminals are open, in what order and which is in front is saved as it changes, so after quitting, a crash or a restart for an update, the next launch reopens them in their folders in the same order, with the same one in front; closed ones stay closed. Only Projects terminals come back, not local terminals opened with ⌘T; split layouts and the programs running in the terminals don’t come back either, so start those again yourself. This works when a bastion host launches ShellRS too, and the external connection’s tab is in front.
- **Keeping terminal output**: when a Projects terminal’s tab closes or ShellRS quits, its last 1,000 lines of output are kept, colors and all. The next time that terminal opens they’re shown first, followed by a dim line, “Above is what this terminal showed when it last closed”, and then the new prompt. If you ran `ls` before quitting, that file list is still there next time. The output is stored as plain text in `terminal-output/` in the data folder and is deleted with its terminal or group; turning off Keep terminal output in Settings › Terminal › Local terminal deletes all of it and keeps nothing more. Limits: if a full-screen program such as vim or htop is open when the terminal closes, nothing is kept (its screen isn’t output); if ShellRS crashes there’s no time to save, so the output kept before stays; Restart doesn’t show the old output.

## File transfer

Once an SSH host’s terminal is connected, the right of its tab bar has two buttons, “Upload files…” and “Download files…”; the tab’s context menu and the terminal’s context menu have them too. Files travel over that terminal’s own SSH connection: no second login, no password or verification code asked again, and jump hosts and proxies work as they do for the terminal.

Transfers use neither SFTP nor `scp`: ShellRS opens further channels on the connection and has the host’s shell run `cat`, `wc`, `mkdir`, `mv` and `find` to send and receive files, so a server without the SFTP subsystem works too. The host needs a POSIX `sh` (Linux, the BSDs, macOS and BusyBox devices have one; Windows hosts aren’t supported). It doesn’t work through a bastion host that allows only one channel; use ZMODEM (`rz` / `sz`) in the terminal there.

- **Uploading**: click “Upload files…”, choose files in the system’s dialog (folders too on macOS), then enter the remote folder they go into. It starts out as the terminal’s current folder when its shell has reported one, and empty otherwise; empty means the login folder, and a leading `~` stands for the login folder. The folder is created if it isn’t there, folders are uploaded with everything in them, and files of the same name are replaced. Each file is first written to a temporary file beside its destination (`name.shellrs-part`) and renamed over it only once it has arrived whole, so a dropped connection or a cancelled upload leaves no half file and the old file as it was. New files keep this computer’s permission bits.
- **Downloading**: click “Download files…”, enter the remote path (a file or a folder) and choose the folder on this computer to save to; it starts out as your Downloads folder. A folder is downloaded with everything in it, and files of the same name are replaced; symbolic links on the host aren’t followed.
- **Progress**: the status bar at the bottom of the window shows the file being copied and its percentage, and says how many more transfers are running; click × beside it to cancel them all. A notification appears when a transfer finishes, fails or is cancelled, with the reason when it failed.
- Transfers share the terminal’s connection, so a large one slows the terminal down. When the terminal disconnects, the transfers going over it stop.
- There is no resuming, no file list, and no renaming, deleting or editing of remote files in the interface: do those with commands in the terminal.

## Download and updates

Packages are on [GitHub Releases](https://github.com/dream10201/shell-rs/releases):

| System | First install | Automatic updates |
|---|---|---|
| macOS (one package for Apple Silicon and Intel) | DMG; drag ShellRS into Applications | Yes |
| Windows x64 | Setup program, which installs for the current user into `%LOCALAPPDATA%\Programs\ShellRS`, with no administrator rights needed | Yes |
| Windows x64 portable | Zip; unzip it into any folder you can write to and run it, with its data in the `data` folder beside it (see “Windows portable” below) | Yes |
| Linux x64 | AppImage | Yes |

ShellRS checks for a new version 30 seconds after it starts, then every 6 hours. When there is one, it downloads and verifies it in the background, and then a green update button appears at the top right of the title bar. Click it: “What’s new” opens the changelog on GitHub, and “Restart to update” switches to the new version and reopens. Restarting closes open connections and stops file transfers and port forwards; the dialog lists exactly which.

“Updates” in “Settings › About” has just three rows:

- **Current version**: below it, the current state (up to date, downloading, downloaded and so on); at the right, the version number and a button, normally “Check for updates”, which becomes “Restart to update…” once an update is downloaded. The build number and platform are in the version number’s tooltip.
- **Update channel**: Stable is for everyday use; Beta gets test versions early, and stable releases too when they come out. After you switch, ShellRS checks the new channel right away (with automatic updates off, it waits until you check by hand).
- **Automatic updates**: when this is off, ShellRS goes online only when you check by hand, and when it finds a new version, you decide whether to download it.

- **Verification**: the update manifest is signed with ShellRS’s release key, and the package is checked against the size and SHA-256 in the manifest; if any step doesn’t match, nothing is installed. On macOS, the new version’s developer signature is checked as well.
- **Privacy**: checking for updates sends only ShellRS’s version number, the operating system and the CPU architecture, nothing that could identify this computer or you. For anonymous usage statistics, see “Privacy”.
- **When automatic updates aren’t possible**: when ShellRS runs straight from the DMG or outside the Applications folder, you can’t write to where it’s installed, on Linux it isn’t run as the AppImage, on Windows it’s neither installed by the setup program nor portable, or it’s a development build you compiled yourself. The About page then says why, and offers “Open download page” when a new version is out.
- **Going back to an older version**: before the database is upgraded to a new schema, it’s backed up as `shellrs.db.v<old version>.bak`. An older version refuses to open a database with a newer schema, so as not to mess up data a newer version saved; to go back, rename the backup to `shellrs.db`.

### Windows portable

The portable copy is a zip (`ShellRS-<version>-windows-x86_64-portable.zip`) holding `shellrs.exe` and an empty `data` folder: unzip it and run `shellrs.exe`, nothing to install. A `shellrs.exe` with a `data` folder beside it is portable: hosts, credentials, settings, `known_hosts`, pasted and generated private keys, the window’s place and update downloads all live in `data`, and nothing goes to `%APPDATA%`. The version number’s tooltip on the About page says “portable”.

- Unzip first: a `shellrs.exe` opened inside the zip has no `data` beside it, so it runs as an ordinary copy and keeps its data in `%APPDATA%\shellrs`.
- Keep it in a folder you can write to, such as `D:\Tools\ShellRS` or a USB stick, not in `Program Files` and not in a folder OneDrive or the like syncs. When the folder can’t be written to, it can’t update itself, and “Open download page” gives the portable zip.
- Don’t rename `shellrs.exe` (updates replace the file by that name) and don’t delete `data` (without it, the copy is no longer portable). A `data` folder in the installed copy’s folder doesn’t make that copy portable (uninstalling deletes the whole folder).
- Automatic updates download and verify in the background as for the installed copy; “Restart to update”, or quitting, swaps `shellrs.exe` and leaves `data` alone. The old files are renamed to hidden names like `.shellrs.exe.old-…` and deleted once the new version has started.
- Use one portable folder from one Windows account at a time. It can run beside the installed copy, each with its own data and its own taskbar button.
- **Moving over from the installed copy**: quit both, then copy the files in `%APPDATA%\shellrs` into the portable copy’s `data`. Pasted and generated private keys switch to the copies in `data\keys` by themselves; on the same computer, saved passwords keep working.
- **What stays on the computer**:
  - Passwords and private key passphrases still go to Windows Credential Manager and don’t travel with the folder: on another computer you enter them again, and passwords saved on someone else’s computer stay there; leave the password empty (asked at each connection) to avoid that. The installed copy shares them: deleting a host or credential in one, or changing its address or username, can remove a password the other still uses, which that one then asks for again.
  - The notification identity Windows records in the registry the first time ShellRS shows a system notification (`HKCU\Software\Classes\AppUserModelId\com.shellrs.ShellRS.Portable`).

## Privacy

ShellRS never sends hosts, credentials, session content, commands, file names or paths, or any identifier that could identify this computer or you. ShellRS itself goes online for only these two things (besides connecting to your hosts):

- **Checking for updates**: sends only ShellRS’s version number, the operating system and the CPU architecture; see “Download and updates”.
- **Anonymous usage statistics**: sent to [Aptabase](https://aptabase.com) to learn how many installs there are, how many devices use ShellRS each day, how the versions are spread, and which features are used most. “Send anonymous usage statistics” in “Settings › About › Privacy” is on by default; turn it off and nothing more is sent, and the counts collected on this computer are cleared too.

With Sync on, ShellRS writes your data, encrypted, to the folder you chose (the cloud drive’s own app uploads it) or uploads it to the WebDAV server or S3 bucket you entered; ShellRS connects to no sync server of its own. The files are encrypted whole, the device’s name (the computer’s), system and ShellRS version included; see “Sync”.

Every statistics event carries ShellRS’s version number and the operating system’s name and version (such as macOS 15.1, Windows 10.0.22631, Ubuntu 24.04). There are only four events:

| Event | When it’s sent |
|---|---|
| `app_installed` | Once, on the first launch. The data folder records that it was reported; a different data folder, or deleting it, reports it again |
| `app_started` | Every launch |
| `app_active` | The first time each day (UTC) the window comes to the front; not again on the day ShellRS started. On macOS, a closed window with ShellRS left in the background doesn’t count |
| `usage` | How many times each feature was used: once 4 hours have passed since the first use, summed up into one event at the next launch, activation or use |

The first three carry these settings and counts, each with a fixed set of possible values: CPU architecture, how ShellRS was installed (setup program, portable, macOS app bundle, AppImage or other), appearance, interface language, light and dark themes (names of built-in themes), whether the interface matches the theme, whether highlighting and automatic updates are on, the update channel, whether any shortcut was changed, and how many hosts, credentials, port forwards and snippets are saved (only as a band: 0, 1-5, 6-20, 21-100, 100+).

`usage` has only counts, no content. It counts: SSH terminals connected (also counted separately for jump hosts, proxies, credentials, no password, quick connections and external connections), local terminals, serial terminals connected, Telnet terminals connected, port forwards started (local, remote, dynamic), file uploads and downloads, ZMODEM uploads and downloads in terminals, opening each of the eleven right sidebar tools, opening a new local terminal in Projects, snippets and history commands sent to the terminal, terminal find, notifications (program, bell, keyword), turning highlighting on and off, and importing hosts from `~/.ssh/config` or `~/.ssh/known_hosts` (how often, not how many hosts).

- Counts are first kept in `analytics.json` in the data folder, so quitting doesn’t lose them, and they’re sent later. Being offline or on an intranet doesn’t get in the way: when sending fails, ShellRS waits 1 minute, then doubles the wait each time up to 6 hours, and retries only while you’re using ShellRS, sending no requests while it’s idle.
- Aptabase infers the country and region from the request’s IP address but doesn’t store the IP. It tells devices apart by a hash of the IP and User-Agent with a random salt that changes every day, so it can’t follow the same device across days.
- Development builds you compile yourself don’t send statistics.
